Les 60 worktrees d'agents

Libère 51G

Ce que j'ai mesuré

Chaque agent lancé en parallèle a reçu une copie complète du dépôt. Il en reste 60, qui pèsent 51G — c'est-à-dire la quasi-totalité des 58G du dossier. Le travail, lui, est ailleurs : sur les 75 branches, 66 sont déjà fusionnées dans main.

Ce que j'ai vérifié avant de proposer

Les 8 branches non fusionnées ont été dépouillées fichier par fichier. Elles touchent en tout 38 fichiers qui n'existent pas dans main : 36 images — vérifiées une à une, aucune n'est appelée par le module auquel elle appartient (ce sont des générations abandonnées, refaites depuis) — et 2 documents de planification (docs/plan-module-n3-horaire.md, docs/plan-module-n5-saisons.md). Par ailleurs 18 worktrees portent des fichiers jamais commités (46 fichiers neufs, dont 46 existent déjà dans main : PowerPoints, fiches, scripts audio produits ensuite par le chemin normal).

Ce que je propose

Récupérer les 2 documents de planification dans docs/, puis retirer les 60 worktrees et les branches qui vont avec.

Le risque

faibleCe qui disparaît est du travail déjà repris dans main ou des images que plus rien n'appelle. À faire quand aucune session n'est en cours dans le dépôt — un worktree retiré sous les pieds d'un agent le casse.

Les gestes

# 1. récupérer ce qui n'existe nulle part ailleurs
git show <branche>:docs/plan-module-n3-horaire.md > docs/plan-module-n3-horaire.md
git show <branche>:docs/plan-module-n5-saisons.md > docs/plan-module-n5-saisons.md
# 2. retirer les worktrees, puis leurs branches
git worktree list | grep .claude/worktrees | awk '{print $1}' | xargs -n1 git worktree remove --force
git worktree prune
git branch -D $(git branch | grep worktree-agent)

Ce qui a été fait

Les deux plans rapatriés dans docs/, puis 60 worktrees retirés (57 dans .claude, 3 dans ~/Claude) et 74 branches supprimées. .claude passe de 51 Go à 4 Ko ; il reste une seule branche, main.

Le paquet git, une fois les branches parties

Libère 3.23 GiB

Ce que j'ai mesuré

L'historique pèse 3.23 GiB pour 30167 fichiers suivis. Tant que les branches d'agents existent, git garde tous leurs objets — y compris les images abandonnées.

Ce que j'ai vérifié avant de proposer

Mesuré par git count-objects -vH, avant tout ménage.

Ce que je propose

Après le chantier précédent, compacter l'historique.

Le risque

nulAucune perte possible : gc ne touche qu'au rangement interne.

Les gestes

git reflog expire --expire=now --all
git gc --prune=now --aggressive

Ce qui a été fait

Fait — et le gain est petit : 3,23 → 3,16 Gio. Je l'avais annoncé plus gros, à tort. L'historique n'était pas gonflé par les branches d'agents mais par le matériel lui-même : images, MP3, PDF et vidéos de main, qui restent dans l'historique par construction. Le seul geste qui les en sortirait est une réécriture de l'historique — un chantier à part, qu'on ne fait pas à la légère sur un dépôt déployé.

La racine : 245 entrées, dont 198 de la même famille

Libère 198 fichiers de moins à la racine

Ce que j'ai mesuré

À la racine du dépôt : 111 scripts generer_audio_*.py et 87 manifestes sons_*.json, pour 245 entrées en tout. Le reste — le serveur, la base, la forge, les pages — se cherche entre les deux.

Ce que j'ai vérifié avant de proposer

Les manifestes sont lus par 10 fichiers (build/audio_manquant.py, build/audio_tous.py, build/collecte_sons.py, build/contenu/module-n8-habitation/_forger_generateur.py, build/contenu/module-n8-recherche/_forger_generateur.py, build/essai_estceque.py), toujours par le même motif RACINE / ('sons_%s.json' % slug) : le rangement se fait en changeant une ligne par fichier, pas en cherchant des chemins partout.

Ce que je propose

Deux dossiers : audio/ pour les scripts de génération, manifestes/ pour les sons_*.json. La racine retombe à une trentaine d'entrées, toutes lisibles d'un coup d'œil.

Le risque

moyenL'audio est gelé, donc rien ne se régénère pendant l'opération. Mais les chemins se vérifient en jouant les contrôles : build/audio_manquant.py doit continuer de rendre zéro module muet.

Les gestes

mkdir -p audio manifestes
git mv generer_audio_*.py audio/
git mv sons_*.json manifestes/
# puis la ligne de chemin dans chacun des lecteurs, et :
python3 build/audio_manquant.py    # doit rester à zéro

Ce qui a été fait

La racine passe de 245 entrées à 39. Douze scripts patchés, une ligne chacun. Contrôle joué : les 86 manifestes sont retrouvés et les 14 813 sons attendus sont tous là. Le piège évité : un chemin resté à la racine ne fait pas échouer le contrôle, il lui fait dire « zéro trou » parce qu'il n'attend plus rien — c'est le nombre de manifestes trouvés qu'il faut lire, pas le nombre de trous.

Les deux manuels de l'élève (40 Mo chacun)

Libère 80 Mo dans le dépôt, et davantage dans l'historique

Ce que j'ai mesuré

assets/documents/manuel-eleve-niveau-4.pdf (1 753 pages) et sa version serrée pèsent 80 Mo à eux deux — les deux plus gros fichiers suivis, loin devant. Ils ne sont liés que depuis la banque de présentations.

Ce que j'ai vérifié avant de proposer

Ce sont des documents dont nous ne sommes pas l'auteur. La règle du projet est claire sur le contenu — le manuel est un modèle de structure, jamais une source à reproduire — mais le fichier, lui, voyage avec le dépôt et se retrouve sur l'hébergeur.

Ce que je propose

Décision à prendre, pas un geste technique : soit les sortir du dépôt et les garder hors ligne, soit assumer leur présence. Les retirer de l'historique est une opération à part, plus lourde (réécriture) — à ne faire que si la réponse est « ils ne doivent pas être là ».

Le risque

à trancherLe lien de la banque de présentations tomberait : il faudrait dire où le manuel se trouve désormais.

Les gestes

git rm --cached assets/documents/manuel-eleve-niveau-4*.pdf
# puis retirer les deux boutons de presentations.html

Ce qui a été fait

Je ne l'ai pas fait, et c'est moi qui avais mal posé la question. Ces deux PDF ne sont pas un document tiers : ils sont produits par notre propre chaîne (build/manuel_eleve.py) à partir des 289 fiches de nos modules. L'argument des droits tombe. Restait le poids — mais git rm --cached ne libère rien : les objets restent dans l'historique. On perdrait un téléchargement qui marche pour un gain nul. À rouvrir seulement si l'on décide de réécrire l'historique, et alors pour tout le matériel, pas pour ces deux fichiers.

Les sauvegardes de données laissées dans data/

Libère trois dossiers

Ce que j'ai mesuré

data/_sauvegarde-avant-demo, data/_sauvegarde-avant-demo-classe et data/sauvegardes gardent l'état des traces d'élèves avant la pose des classes de démonstration.

Ce que j'ai vérifié avant de proposer

Les classes de démonstration se posent et se retirent par script (--install / --purge) : ces copies ne servent plus de filet.

Ce que je propose

Les retirer, ou les dater et les sortir de data/.

Le risque

faibleCe sont des traces fictives ; aucune donnée d'élève réel.

Les gestes

rm -rf data/_sauvegarde-avant-demo data/_sauvegarde-avant-demo-classe

Ce qui a été fait

Les trois dossiers sont sortis dans ~/Claude/archives-menage-2026-08-30 — déplacés, pas supprimés. data/ passe de 3,4 à 2,7 Mo.

L'ordre compte. Les worktrees d'abord, le compactage ensuite — l'inverse ne libère rien, puisque git garde les objets tant qu'une branche les tient. Et rien de tout cela pendant qu'une session travaille dans le dépôt : plusieurs sessions partagent cet arbre.

Relancer python3 build/menage_proposition.py refait les mesures et réécrit cette page. Les décisions, elles, vivent dans le navigateur de ce poste : elles survivent à une régénération, et le bouton « Exporter » les sort en JSON.
